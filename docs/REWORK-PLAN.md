# Allvision Academy — план реворка (пошаговая инструкция)

Этот документ — самодостаточная инструкция для любого агента (Claude Code, Codex и т.п.),
работающего в этом репозитории. Прочитай его целиком перед началом любого этапа.
Актуальный статус этапов — в шапке `CLAUDE.md` (секция «План этапов Academy»);
после завершения этапа обновляются ОБА файла.

---

## 1. Контекст

**Было**: Allvision Studio — AI-фабрика цифровых подарков (услуги на fal.ai/PiAPI, коины,
витрина, чат Allvision AI, Студия). Прод живёт на `https://allvision-pulse.ru`.

**Становится**: Allvision Academy — персонализированная онлайн-школа. Ребёнок проходит
учебную программу внутри интерактивного приключения вместе с живым преподавателем:
нейросети создают реалистичного персонажа с внешностью ребёнка, позы, сюжетные
иллюстрации и кат-сцены; учитель ведёт занятие по видеосвязи и управляет сценами;
браузерная игра (PixiJS) превращает материалы в интерактивный урок.
Направления: английский, нейросети/AI-контент, программирование, позже школьные предметы.

**Точка отката**: git tag `v0.2-allvision-studio-final` (полное состояние Studio).

**Полная продуктовая концепция** (17 разделов: типы пользователей, структура урока,
конструктор сцен, библиотеки, AI-персонаж, проведение занятия, примеры уроков,
геймификация, запись/расписание, цены, мессенджер, защита данных, архитектура,
надёжность, очерёдность) — дана владельцем в переписке; ключевые выжимки продублированы
в описаниях этапов ниже. При сомнении в продуктовой детали — спросить владельца.

## 2. Зафиксированные решения (не пересматривать без владельца)

| Область | Решение |
|---|---|
| Бэкенд | Остаётся Express + Prisma + BullMQ (НЕ NestJS). Сохраняем боевой AI-слой (fal/PiAPI, прокси, ретраи, AIUsageLog, капы), auth, платежи, деплой |
| Движок сцен | PixiJS, кастомный редактор слоёв + событийная логика «событие → условие → действие» |
| Видеосвязь | Self-hosted LiveKit; план Б — внешний сервис |
| Дизайн | Светлая бело-оранжевая премиальная тема. Токены: `.academy-theme` в `apps/web/src/app/globals.css`. Studio-экраны остаются тёмными до катовера |
| Ход реворка | Аддитивно в `main`: новые модели/роуты рядом с legacy, прод рабочий всё время. Катовер фронта — этап A11 |
| Роли | Родитель = `User` с ролью `PARENT` (новые регистрации). Ребёнок = `ChildProfile` (НЕ User). `TEACHER`, `METHODIST` — роли User. Legacy `USER` действует как родитель |
| Деньги Academy | Предоплаченный баланс занятий (не коины): 25 мин — 1000₽, 45 мин — 1500₽, пакеты 4/8/16 со скидками 3/7/12%. Преподавателю 30% фактической стоимости. Детали — этап A4 |

## 3. Правила работы в этом окружении (ОБЯЗАТЕЛЬНО)

Окружение: Windows 11, PowerShell — основной shell (доступен и bash). Монорепо npm workspaces.

1. **Pre-flight перед любыми изменениями**: прочитать текущее состояние затрагиваемых
   файлов (schema.prisma, роут, компонент). Не предполагать — проверять.
2. **Git-дисциплина**: push в `main` БЕЗ `[skip ci]` в HEAD-коммите запускает ПЛАТНЫЙ
   GitHub Actions деплой на прод. Поэтому: все промежуточные коммиты — с `[skip ci]`
   в сообщении; деплой — осознанно на границе этапа (вручную по SSH, см. §7, либо
   одним push без [skip ci] с согласия владельца).
3. **Postgres локально НЕ поднят** (`localhost:5433` недоступен, Docker daemon не
   запущен). Следствия:
   - миграции пишутся ВРУЧНУЮ в `packages/database/prisma/migrations/<timestamp>_<slug>/migration.sql`
     (формат имени: `YYYYMMDDHHMMSS_a<N>_<что>`), схема и SQL должны совпадать;
     применяются на проде автоматически (`prisma migrate deploy` в CMD api-контейнера);
   - DB-backed тесты (api, worker pipeline-runner) пишутся, но локально НЕ гоняются —
     фиксировать в CLAUDE.md «прогнать на проде/CI»;
   - `npx.cmd prisma generate --schema packages/database/prisma/schema.prisma` — гонять
     после изменения схемы; если запущен dev-сервер проекта, будет Windows EPERM
     (остановить dev). Чужие node-процессы (vite и т.п.) не мешают.
4. **Проверки перед коммитом этапа** (все должны быть зелёными):
   - `npm.cmd run build -w @allvision/shared -w @allvision/database -w @allvision/api -w @allvision/worker -w @allvision/web`
     (можно по одному; web иногда падает Windows-ошибкой `3221225477` — повторить);
   - юнит-тесты незаблокированных пакетов: `npm.cmd test -w @allvision/shared -- --runInBand`,
     worker без DB-backed: `npm.cmd test -w @allvision/worker -- --runInBand --testPathIgnorePatterns="pipeline-runner|piapi-provider"`.
5. **После каждого этапа**: секция «Этап A<N> ✅» в конец `CLAUDE.md` (что сделано,
   нестандартные решения, результаты проверок, долги) + отметка ✅ в шапке CLAUDE.md
   и в этом файле + git commit `[skip ci]`.
6. **Mock-first**: новые AI-операции сначала проверяются с `PROVIDER_MODE=mock`
   (MockAIProvider), реальный fal — на проде. В `NODE_ENV=test` — StubAIProvider,
   сетевых вызовов нет.
7. **Данные детей**: исходные фото и производные персонажа — ТОЛЬКО закрытое хранилище
   (`private-uploads/`, вне nginx `/static`), выдача через авторизованные эндпоинты
   с ownership-проверкой. Никогда не класть детские материалы в `MediaAsset.publicUrl`
   или `uploads/`.
8. **Локализация**: весь пользовательский UI и сообщения ошибок — на русском.
   Технические слаги/статусы — латиницей.

### A2 ✅ AI-профиль персонажа — СДЕЛАН

См. секцию «Этап A2» в CLAUDE.md. Реализовано: `CharacterProfile`/`CharacterReference`

выдачи файла; нет admin-обзора персонажей.

<details><summary>Исходная постановка A2 (справочно)</summary>

**Цель**: из загруженных фото ребёнка создаётся утверждаемый «профиль внешности» —
эталонный набор изображений, который дальше используется всеми генерациями.

**Продуктовые требования** (раздел 7 концепции): эталонный портрет, профиль, три
четверти, полный рост, нейтральная поза, базовая одежда, несколько выражений лица.
Стиль — «реалистичный ребёнок внутри кинематографического анимационного мира», не
плоская мультяшка. Родитель или преподаватель утверждает результат; неудачные варианты
удаляются и перегенерируются.

**Задачи**:
1. Prisma: `CharacterProfile` (childId unique, status DRAFT|GENERATING|READY|APPROVED|FAILED,
   progress, errorMessage, approvedAt) и `CharacterReference` (profileId, kind:
   portrait|profile_side|three_quarter|full_body|neutral_pose|expression_joy|expression_surprise...,
   storageKey в ЗАКРЫТОМ хранилище `private-uploads/characters/<parentId>/<childId>/`,
   width/height, promptUsed, costUsd). Миграция вручную.
2. Хранилище: расширить/продублировать `child-photo-storage.ts` под каталог персонажа
   (`CHARACTER_REFS_DIR` или общий `PRIVATE_UPLOADS_DIR`). Выдача — только авторизованный
   эндпоинт (родитель-владелец, ADMIN; позже TEACHER назначенного ученика).
3. Worker: очередь `character-profile` + процессор. Вход: childId. Читает фото ребёнка
   из private-хранилища (worker получает mount!), готовит data-URI (sharp downscale ≤2048),
   для каждого kind вызывает `AIProvider.imageEdit` (fal nano-banana по умолчанию;
   модель конфигурируема) с identity-промптом, пишет результат в закрытое хранилище,
   создаёт `CharacterReference`, двигает progress, публикует SSE-событие.
   Ошибка любого шага → статус FAILED + errorMessage, частичные референсы сохраняются.
   Все вызовы логируются в `AIUsageLog` (blockSlug `character-profile`).
4. Compose/env: worker-контейнеру bind mount `/opt/allvision-studio/shared/private-uploads:/app/private-uploads`;
   env `CHILD_PHOTOS_DIR`, `CHARACTER_REFS_DIR` в worker .env.example.
5. API `/api/family/children/:childId/character`:
   - `GET` — профиль + референсы (с авторизованными fileUrl);
   - `POST /generate` — требует все 5 согласий и ≥1 фото; создаёт/перезапускает профиль,
     ставит job (повторный запуск при GENERATING — 409);
   - `POST /approve` — READY → APPROVED;
   - `DELETE /references/:refId` — удалить неудачный референс;
   - `POST /references/:refId/regenerate` — перегенерация одного kind;
   - `GET /references/:refId/file` — стрим файла.
6. Web `/family`: блок «AI-персонаж» в карточке ребёнка — статус, прогресс-бар (SSE/поллинг),
   сетка референсов с подписями, кнопки «Создать персонажа», «Утвердить», per-ref
   «Перегенерировать»/«Удалить». Тема `.academy-theme`.
7. Промпты: базовые identity-промпты по kind — в shared-константе
   (`packages/shared/src/academy/character.ts`), русские подписи kind'ов там же.

**DoD**: локально с `PROVIDER_MODE=mock` полный цикл (фото → генерация → референсы →
утверждение) проходит; чужой родитель получает 404; билды зелёные.
**Тесты**: shared (промпты/kind'ы), api DB-backed (гейты согласий/фото, ownership,
статусные переходы), worker (процессор с MockAIProvider).
**Риски**: identity-похожесть на mock не проверить — реальный смоук на проде первой
генерацией; стоимость полного набора ~$0.8–1.5 (nano-banana) — заложить лимит на
профиль (env, дефолт $3) поверх дневного капа.

### A3 — Программы и прогресс

**Цель**: методист ведёт программу в админке; система знает прогресс ребёнка по навыкам
и рекомендует следующую тему.

**Задачи**:
1. Prisma: `Enrollment` (childId+courseId, статус, startedAt), `TopicProgress`
   (enrollmentId+topicId, status: locked|recommended|in_progress|completed, completedAt,
   teacherNote), `SkillProgress` (childId+skillId, level 0..3, updatedAt),
   `TopicChangeLog` (кто сменил рекомендацию, причина: repeat|gap|parent_wish|special_project).
2. Рекомендация: сервис `next-topic.ts` — первая незакрытая тема по sortOrder с учётом
   prerequisites (`Topic.content.prerequisites: string[]` ids); преподаватель может
   переопределить с обязательной причиной (пишется в TopicChangeLog).
3. Admin UI `/admin/curriculum`: дерево Направление→Курс→Модуль→Тема, CRUD-формы
   (API из A1 уже готов), редактор навыков темы, длительность 25/45, AI-бюджет.
4. API для будущих кабинетов: `GET /api/family/children/:id/progress` (курсы, темы,
   навыки), `GET .../next-topic`.
5. Web: вкладка прогресса ребёнка в `/family` (курсы, пройденные темы, навыки в виде
   «знает числа 1–10» с уровнями).

**DoD**: методист собирает курс в админке; enrollment создаётся; рекомендация считается
и переопределяется с причиной. **Тесты**: shared (алгоритм next-topic на фикстуре),
api (CRUD + прогресс + переопределение с причиной).

### A4 — Запись и деньги

**Цель**: родитель записывает ребёнка на урок к преподавателю и оплачивает пакетами занятий.

**Продуктовые требования** (разделы 11–12): flow как запись в салон (ребёнок → предмет →
длительность → преподаватель → слот → рекомендуемая тема → оплата/списание → диалог);
статусы урока `BOOKED → AWAITING_PREP → GENERATING → READY → IN_PROGRESS → COMPLETED →
REPORT_SENT` (+ CANCELLED_*, NO_SHOW); цены 25мин=1000₽/45мин=1500₽, пакеты
1/4/8/16 занятий со скидками 0/3/7/12%; баланс занятий непереводим и невыводим;
после урока: списание, преподавателю начисляется 30%, AI-затраты пишутся отдельно;
правила отмены/переноса/неявки.

**Задачи**:
1. Prisma: `TeacherProfile` (userId unique, subjects, bio, isActive),
   `TeacherSlot` (teacherId, weekday/время или конкретные даты, повторяемость),
   `Lesson` (childId, teacherId, topicId?, durationMin 25|45, startsAt, status,
   priceRub, cancellation-поля), `LessonBalance` не нужен как таблица — считать из
   `LessonCredit` (parentId, durationMin, source: purchase|refund|manual, lessonId?,
   ±1, expiresAt?) либо агрегатное поле; `LessonPackage` (каталог пакетов),
   `TeacherEarning` (lessonId, teacherId, amountRub, status: pending|available|paid|rejected).
2. Платежи: новый `PaymentPurpose.LESSON_PACKAGE`, интеграция с существующим
   ЮKassa-flow; idempotent webhook уже есть — расширить обработку.
3. API: `/api/academy/teachers` (публичный список с фильтром по предмету),
   `/api/academy/booking` (свободные слоты, создать запись, отменить/перенести по
   правилам), `/api/academy/packages` + покупка; списание кредита при записи,
   возврат при отмене по правилам.
4. Кабинет преподавателя (первая версия): `/teacher` — календарь, настройка слотов,
   список предстоящих уроков со статусами.
5. Web родителя: мастер записи (5 шагов) + баланс занятий и покупка пакетов в `/family`
   или `/profile`.
6. Правила отмен (дефолт, уточнить у владельца): отмена ≥8ч до урока — возврат кредита;
   позже — сгорает; отмена преподавателем — возврат всегда + уведомление; неявка
   ученика — списание.

**DoD**: полный happy-path на mock-ЮKassa: покупка пакета → запись → слот занят →
преподаватель видит урок. **Тесты**: api (слоты/коллизии брони, списание/возврат
кредитов, идемпотентность webhook).
**Риск**: таймзоны — хранить UTC, отображать в Europe/Moscow (дефолт), заложить поле tz.

### A5 ✅ — Панель генерации и библиотеки

**Цель**: преподаватель/админ генерирует учебные материалы (фоны, предметы, NPC, позы
ребёнка, сцены с ребёнком) и всё автоматически попадает в правильную библиотеку.

**Продуктовые требования** (раздел 6): типы генераций (фон, предмет, NPC, поза, сцена
с ребёнком, прозрачный фон, ключевой кадр, вариация, замена области, апскейл);
параметры (модель, стиль, системный промпт, пользовательское описание, референсы,
персонаж ученика, поза, одежда, эмоция, ракурс, свет, формат, количество, качество,
допустимая стоимость); результат автоматически: storage → превью → библиотека →
метаданные (модель/промпт/стоимость) → привязка к ученику или общей коллекции.
Три библиотеки: общая (обезличенная), преподавателя (черновики), персональная ученика
(в закрытом хранилище). Персональное НИКОГДА не попадает в общую автоматически.

**Задачи**:
1. Библиотеки: общая и преподавателя — на `MediaAsset` (новые kind:
   `academy-background|academy-prop|academy-npc|academy-effect|academy-audio`,
   `ownerUserId` = преподаватель для личной). Персональная ученика — НОВАЯ таблица
   `ChildAsset` в закрытом хранилище (kind: pose|scene|cutscene|project, childId,
   storageKey, промпт/модель/стоимость, sourceRefIds).
2. Генерация: переиспользовать паттерн `Project`/`service-pipeline` ЛИБО отдельная
   очередь `academy-generation` (решить по месту; критерий — не ломать Studio-статистику).

### A6 — Конструктор интерактивных сцен (САМЫЙ БОЛЬШОЙ ЭТАП)

**Цель**: методист/преподаватель собирает интерактивный урок из сцен; движок PixiJS
воспроизводит сцену у ученика и преподавателя.

**Продуктовые требования** (разделы 4–5): пять зон интерфейса (маршрут урока слева,
рабочая область по центру, свойства справа, состояния/анимации/события снизу, генерация/
предпросмотр/версии/публикация сверху). Слои: фон/анимированный фон/видео/передний план/
изображения/персонаж/NPC/предметы/текст/диалоги/кнопки/карточки/поля ввода/индикаторы/
таймер/прогресс/частицы/звук/зоны нажатия/столкновения/платформы. У элемента: позиция,
размер, поворот, прозрачность, слой, адаптивное закрепление, состояния, анимации
появления/исчезновения, доступность ученику, видимость учителю, реакции.
Логика: событие→условие→действие (события: нажатие, клавиша, drag, правильный/
неправильный ответ, таймер, действие учителя, конец видео, результат AI, выполнение
кода; действия: показать/скрыть, звук, смена позы, анимация, очки, подсказка, смена
состояния, разрешить переход, следующая сцена). Режимы проверки: авто/преподаватель/
смешанная/голос+подтверждение/творческий. Версии шаблонов: изменение оригинала не
ломает подготовленные занятия. Преподаватель кастомизирует экземпляр (сюжет, внешний
вид, скрытие сцен, сложность), но НЕ образовательные цели/системные правила/защищённые
промпты.

**Рекомендуемая разбивка**:
- **A6.1 Формат сцены + рантайм-ядро**: JSON-схема сцены (zod в shared:
  `packages/shared/src/academy/scene-format.ts`) — слои, элементы, состояния,
  правила событие→условие→действие. PixiJS-плеер (`apps/web/src/lib/scene-engine/`):
  загрузка сцены, рендер слоёв, обработка событий, машина состояний. Витринный
  тест-плеер на тестовой странице.
- **A6.2 Редактор**: страница `/constructor` (методист/админ): канвас с drag/resize/
  rotate, панель слоёв, инспектор свойств, редактор правил (визуальные списки
  событие→условие→действие), привязка ассетов из библиотек A5, автосохранение,
  undo (командный стек), предпросмотр ученика/преподавателя.
- **A6.3 Шаблоны и версии**: Prisma `LessonTemplate` (topicId, title, статус
  draft|published, защищённые поля), `LessonTemplateVersion` (immutable снапшот
  сцен JSON), `LessonInstance` (lessonId, versionId, персонализированные оверрайды,
  подставленный childId-персонаж). Публикация = новая версия. Экземпляр урока
  ссылается на конкретную версию.
- **A6.4 Типы сцен первого релиза**: сюжетная иллюстрация, теория, выбор ответа,
  карточки, drag-and-drop, поиск пары, сортировка, кодовый замок, ввод текста,
  финал/награждение. (Платформер, видео-кат-сцены на таймлайне, AI-лаборатория,
  редактор кода — второй этап концепции, НЕ сейчас.)

**DoD**: методист собирает «Замок чисел» (пример из концепции: свиток → теория чисел →
соединение цифр со словами → кодовый замок → награда) целиком в конструкторе;
играется в тест-плеере. **Тесты**: shared (валидация формата сцены, машина состояний
на фикстурах — это ЮНИТ-тестируемо и критично), минимальные UI-тесты по возможности.
**Риск**: скоуп-крип — жёстко держаться типов A6.4; всё «сверху» — в бэклог.

### A7 — Проведение урока (синхронизация)

**Цель**: преподаватель и ученик видят одну сцену; учитель управляет, ученик
взаимодействует; всё переживает реконнект.

**Продуктовые требования** (раздел 8): экран = камеры + интерактивное окно. Панель
учителя: пред/след сцена, разблокировка задания, верно/неверно, подсказка, повтор,
смена сложности, смена позы, запуск видео, награда, заметка, завершение. Ученик:
кнопки, клавиатура, перетаскивание, ввод, эмоции-реакции. Управление преподавателя
главное; переход к следующему слайду — только по решению учителя (даже при авто-проверке).
Восстановление с последнего состояния при переподключении. Материалы предзагружаются.
Запись звонков по умолчанию выключена.

**Задачи**:
1. WebSocket-сервер: `ws` или socket.io в api-процессе (или отдельный процесс) —
   комнаты `lesson:<id>`, роли teacher/student, авторизация по JWT.
2. Состояние урока: `LessonRuntimeState` в Redis (текущая сцена, состояние сцены,
   очки, флаги разблокировки) + периодический снапшот в Postgres (`Lesson.runtimeState`).
   Источник истины — сервер; клиенты применяют патчи.
3. Протокол: teacher-команды (nextScene, unlock, markCorrect, hint, reward...),
   student-события (interaction, answer), сервер валидирует по роли и текущему
   состоянию, рассылает патчи.
4. Страницы `/lesson/:id/teacher` и `/lesson/:id/student` (детский упрощённый UI):
   сцена-плеер A6 + панель учителя / интерактив ученика. Предзагрузка всех ассетов
   версии урока до старта (манифест из LessonTemplateVersion).
5. Pre-flight урока (раздел 16): чек до старта — все сцены опубликованы, файлы
   доступны, видео обработаны; резервный универсальный материал при неготовности.
6. Статусы Lesson: READY → IN_PROGRESS (первый вход учителя) → COMPLETED (кнопка
   завершения) — интеграция с A4.

**DoD**: два браузера (teacher/student) проходят «Замок чисел» синхронно; обрыв
соединения ученика восстанавливает состояние. **Тесты**: протокольные юнит-тесты
редьюсера состояния урока (shared), интеграционный на WS-сервер.

### A10 — Отчёты, мессенджер, выплаты, удаление данных

**Цель**: закрыть операционный контур: родитель информирован, преподаватель получает

**Задачи**:

2. Мессенджер: диалог родитель↔преподаватель, создаётся при первой записи;
   `Thread`/`ThreadMessage` (НЕ переиспользовать AI-чат `Chat`); системные сообщения
   (запись, перенос, урок готов, отчёт); вложения-изображения; админ может войти в
   диалог; ребёнок — только безопасный режим (read-only в A10). Личные контакты
   ребёнка преподавателю не передаются.
3. Выплаты: на базе `TeacherEarning` (A4) — админ-страница `/admin/payouts`: период,
   суммы по преподавателям, статусы (ожидает подтверждения → доступно → выплачено /
   отклонено-корректировка), отметка выплаты с прикреплением подтверждения (5-го числа,
   вручную).
4. Удаление данных (раздел 14): кнопка у родителя «удалить материалы ребёнка» и

   кат-сцены, кэш, незавершённые генерации (worker-джоба очистки + журнал
   `DeletionLog`); учебная статистика обезличивается (childId → null/hash), финансовые
   записи остаются. Журнал просмотров/генераций детских материалов (`AccessLog`) —
   минимум: кто/когда смотрел файл персонажа.

**DoD**: полный цикл: урок → отчёт → родитель прочитал; выплата отмечена; удаление
ребёнка зачищает все файлы (проверка листингом каталогов). **Тесты**: api (каскад
удаления с файлами, права мессенджера, статусы выплат).
